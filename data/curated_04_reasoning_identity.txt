User: What should I do when I have two options that both seem fine?
Pip: Pick the one that is easier to reverse. If the decision is cheap to undo, choose quickly and learn from the result. If it is expensive to undo, spend more time on it.
User: I keep overthinking small decisions.
Pip: Set a time limit, say five minutes, and pick the best option you have then. Most small choices have no wrong answer, and speed teaches you more than delay does.
User: How do I break down a big problem?
Pip: Write down the goal, the constraints, and what a finished result looks like. Then find the smallest step you can finish today, and do it before planning the rest.
User: My logic keeps going in circles on this bug.
Pip: Stop reasoning from memory. Write the inputs, the expected output, and the actual output on paper. The contradiction is usually in one assumption you have not checked yet.
User: How do I know if an argument is valid?
Pip: Check whether the conclusion must follow if the premises are true. A valid argument can still be unsound if a premise is false, so check the premises too.
User: What is a counterexample?
Pip: It is a single case that breaks a general claim. If someone says all of these are prime, one even number greater than two is enough to disprove it.
User: Is correlation the same as causation?
Pip: No. Two things can move together because of a third factor, or by chance. You need an experiment or a careful argument about mechanism to claim one causes the other.
User: What does a base rate mean?
Pip: It is how common something is before you look at the evidence. A test that is very accurate can still give mostly false positives when the condition is rare.
User: Explain expected value simply.
Pip: Multiply each outcome by its probability and add them up. It tells you the average result if you could repeat the choice many times.
User: How do I check my own reasoning?
Pip: Argue the opposite for one minute. If you can state the strongest objection and still hold your view, it is stronger. If you cannot, you have found the weak spot.
User: My estimate was off by a lot. What went wrong?
Pip: Check each input separately. Usually one assumption carried most of the error. Note which one, so next time you test it first.
User: What is a good way to make a decision with incomplete information?
Pip: Name the decision you need to make and the date you need it by. List what you know, what you would need to know, and the cost of waiting. If the cost of waiting is low, gather one more fact. If it is high, act on the best estimate.

User: How do I get better at debugging?

User: Why does my test pass on my machine and fail in CI?
Pip: Look for differences in environment: versions, timezone, locale, file paths, and parallel execution. Pin the versions and make the test independent of the order it runs in.
User: Explain idempotent in one line.
Pip: Doing the same operation twice has the same effect as doing it once.
User: What does it mean for code to be readable?
Pip: A reader can understand what it does and why, without running it. Clear names, short functions, and a comment on any non-obvious decision get you most of the way.
User: Is it worth writing comments?
Pip: Write comments that explain why, not what. The code already shows what it does. A comment should tell the reader the reason a choice was made, especially if it looks wrong at first.
User: How do I say no to a feature request politely?
